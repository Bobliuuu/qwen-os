# Model-decoded pixels: 8 contiguous DOOM frames emitted by the Qwen model

Status 2026-11-05: **12 frames (clip frames 2-4 and 12-20, E1M1) have their pixel bytes emitted by the real Qwen3.5-4B checkpoint as console BYTE tokens, in lockstep with the oracle, and the decoded view is byte-identical to the emulator's frame.** The other 33 of the 45 clip frames were NOT done (cost, see below). The earlier clip (README) is unchanged: there Qwen verified the instruction trace and the emulator read the pixels.

## What is the model, what is the host

1. Host: takes the verified start state of frame N (the pickled machine state right before the frame, from the stored per-segment snapshots, ELF e3eb1282..., chunk-ROM plan af843bac...) and writes ONE guest variable, `q_dump_req = 1`, into its RAM. This arms the guest's own serial LCD dump (ports/doomdmc/qlcd.c). (The `p` key path panics in this build, so the flag is poked directly: a host RAM write at the snapshot, disclosed.)
2. Host: runs the reference machine once to learn the expected trace, and cuts the frame into 6 sub-segments at not-yet-executed pcs (ROM `ebreak` breakpoints, the same mechanism as the stop hook) so they can run on parallel GPUs. Each sub-segment starts from a host state (host-supplied snapshot, as in every chunk of the clip).
3. **Model**: executes the guest instructions (~2.2-2.5M instructions per frame: the whole frame render plus the dump routine; the render itself is the same code the verified clip ran). The guest's dump routine writes the frame's palette-index pixels with its own PUTC calls. Every console byte is a chip BYTE token **generated by the model** (verified one by one against the oracle; the segment fails if any token differs). We save those generated bytes (`model_emitted_bytes_all_in_run_order.bin`, `model_stream_NN.bin`). Per frame: 32,100 model-emitted bytes (32,887 for frame 16, which also redraws part of the status bar).
4. Oracle (host, lockstep): compares every model token; also required per sub-segment: instruction count and BYTE tokens equal the host reference (`console.bin == console.bin.model`, asserted).
5. Host: parses the byte stream (0x01 P/W/D/E records, palette-index columns), maps palette index -> RGB with the PLAYPAL of the IWAD (`tools/lowres_frames.py`) and writes the PNG. This colour mapping is the only host-side pixel step. Sub-segment boundaries and the `q_dump_req` write are host actions.

Why not "read RAM": the 160x200 frame is never resident in the guest's 32 KiB RAM; DOOM streams column strips straight to the LCD pump. Only a 32x24 thumbnail lives in RAM. So the pixels can only come out of the model as the guest's own dump stream, which is what is done here.

## Cost

- 14 container runs on Modal A100 (40/80 GB), K=64 CUDA-graph executor (`--k-graph 64`), 331 container-minutes in total (19,883 s), roughly 5.5 GPU-hours, about 12-14 USD estimated (not billed-measured).
- About 3.1-3.5M chip tokens per frame (~1.38 tokens/instr), about 1,600-1,700 chip tokens/s per container on the first 3 runs (A100-80GB) and ~1,200-1,300/s on the A100-40GB ones. Wall for the 8 frames: about 55 minutes (two batches of 6 and 8 parallel runs; a frame is ~3.3M tokens, about 25-30 container-minutes, a frame cut 6-way takes ~5-15 min).
- All 45 frames at this price: 45 x ~28 container-min = ~21 container-hours (~50 USD), plus the first frames cost more (level load).

## Reproduce

```
# 1. start states: out/model snapshots (Modal volume qwenos-snaps seg<N>.pkl, N = frame+3), per frame:
PYTHONPATH=<qwenputer>/experimental/riscv python3 tools/model_fbdump.py split --elf build/qwenos-e1m1.elf \
   --sym-elf build/doomd-sym.elf --snaps DIR --seg 17 --parts 6 --first-index 1 --out OUT      # frame 14 = seg 17
# 2. model runs (one container per index range; modal volumes: qwenos-q4-rv1, qwenos-bundle/mp, qwenos-mpsnaps):
modal run tools/modal_fbdump.py --tag mp2 --ranges 1:5,5:9,9:13,13:17,17:21,21:25 --snapdir mps
# 3. decode + compare with the emulator frames:
python3 tools/model_fbdump.py decode --model-bytes <console.bin.model ...in range order> --frames 14,13,15,12 \
   --frame-lengths 32100,32100,32100,32100 --wad freedoom1.wad --emu-frames out/clip/frames --out out/clip_modelpixels
python3 tools/make_mp_video.py out/clip_modelpixels docs/assets/qwenos-doom-modelpixels 12,13,14,15,16,17,18,19
```
`tools/model_doom_qwen.py` additionally writes `<out>.model` (the model's own BYTE tokens). The driver is the K-token one from `perf/ktoken` (branch base).

## Caveats

- Sub-segment start states and `q_dump_req` are host-written; the frame's pixels are produced by guest code running on the model from the verified state before that frame. The state before frame N was itself verified in the clip run (not re-proved here).
- The dump-armed frame runs ~10% more instructions than the production frame (dump routine); instruction counts of the production clip are unaffected.
- Not covered: frames other than 2-4 and 12-20, the status bar, the frame-1 level load.
